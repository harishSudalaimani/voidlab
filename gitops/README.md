# VoidLab GitOps

Argo CD manages platform projects, application definitions, and cluster policies from this directory. `bootstrap/root-application.yaml` uses the `bootstrap` AppProject. Networking, security, storage, and observability each have their own AppProject under `projects/<project>/`; applications use the matching project and never Argo CD's built-in `default` project. The root Application includes YAML under `projects/`, `applications/`, and `policies/`. Helm values under `values/` are read by child Applications and are not applied directly.

## Storage and platform deployment order

Argo CD applies child Applications in sync-wave order and waits for each Application to become Healthy before starting the next wave:

1. Longhorn (`storage`, wave 0)
2. CloudNativePG operator (`storage`, wave 1)
3. Shared PostgreSQL cluster (`storage`, wave 2)
4. Shared Redis service (`storage`, wave 3)
5. Self-hosted Infisical (`security`, wave 4)
6. Infisical Secrets Operator (`security`, wave 5)
7. MinIO (`storage`, wave 6, currently paused)

The ordering depends on Application and CloudNativePG Cluster health checks enabled in the Argo CD Helm values managed by `infra/argocd/pulumi`. Apply the Argo CD Pulumi update before relying on these waves. The CloudNativePG Cluster check waits for its `Ready=True` condition, so the shared data services are ready before Infisical starts.

Longhorn's default `longhorn` StorageClass uses two replicas because the cluster has two storage nodes. Its pre-upgrade chart hook is disabled in the values file and enforced as an Argo CD Helm parameter, because that hook can run before the service account exists on a fresh GitOps install. The chart settings are in `values/storage/longhorn/values.yaml`; the Argo-specific override is in `applications/storage/longhorn/application.yaml`.

### Longhorn disks and node placement

Kubernetes bootstrap prepares Longhorn's `open-iscsi` and NFS prerequisites on both Fedora nodes. It requires the existing `/data/vms` SSD and `/storage` HDD mounts on `cp`, stores containerd images on the SSD, and creates Longhorn directories under both mounts; `worker` uses `/var/lib/longhorn` on its root disk. Longhorn disk annotations reserve no extra capacity, and volumes use two replicas across `cp` and `worker`. Longhorn's user-facing control components run on `cp`; its storage manager and system-managed storage components can run on both nodes. Longhorn may consume all reported free disk space, so filling a disk, especially the worker root disk shared with Fedora and Kubernetes, can affect the node.

Argo CD, Cilium's operator, Hubble Relay/UI, Longhorn's control components, the CloudNativePG operator, and the Infisical Secrets Operator are pinned to `cp`. The Cilium agent and Envoy DaemonSets run on both nodes because each node needs the network datapath. Ordinary application pods are pinned to `worker` where configured, and the Kubernetes control-plane taint keeps the remaining application pods off `cp`. The PostgreSQL cluster tolerates that taint and requires its two instances to run on different hosts, placing one replica on each server.

### Shared PostgreSQL and Redis

The `storage` project owns shared data services in the `database` namespace. It installs CloudNativePG chart `0.29.2` (operator `1.30.2`) on `cp` and creates a two-instance PostgreSQL cluster on Longhorn, with one instance required on each physical server. The instances tolerate the control-plane taint so the database can use both nodes; required host anti-affinity prevents both replicas from sharing one server. The initial database and role are `infisical`; future services should get their own database and role on this same cluster, with credentials delivered to their namespace through the secrets platform. This isolates each service's database objects while reusing the PostgreSQL cluster. The CNPG application is named `postgresql-cluster`, independent of any consuming application. Infisical reads the `postgresql-app` Secret generated by CNPG; future apps should not reuse that role.

The shared Redis service is a single Redis instance on Longhorn. It requires `REDIS_PASSWORD` in the `platform-secrets` Secret in namespace `database`; use a 64-character hex value so it is safe in the Redis URL. A NetworkPolicy allows Redis connections only from namespaces labelled `platform.voidlab.io/shared-redis-client: "true"`; label future workload namespaces when they are authorized to use Redis. Infisical currently uses Redis database index `0`; assign another logical database or a service-specific key prefix to future consumers. Redis is a single replica and therefore a shared availability limit.

PostgreSQL backups are not configured yet; add an S3-compatible backup destination after MinIO is resumed or another target is chosen.

The infrastructure code currently selects Kubernetes `1.37`. CloudNativePG `1.30.x` lists Kubernetes `1.34`–`1.36` as supported and `1.37` as tested, but not supported. The pinned operator is the latest stable release at this revision, but that Kubernetes support caveat still applies.

Infisical's web UI and API run in the same service. The server pods are pinned to `worker`; the service remains internal (`ClusterIP`) with no ingress or NodePort. For initial UI access, run `kubectl -n database port-forward svc/infisical 8081:8080` and open `http://localhost:8081`. `SITE_URL` is set to that local address. Before the shared Redis service and Infisical can become healthy, provide a `platform-secrets` Secret in namespace `database` with `REDIS_PASSWORD`, `ENCRYPTION_KEY`, and `AUTH_SECRET`. The Redis password is shared platform configuration; the other two keys bootstrap Infisical, which cannot provide its own initial credentials. Keep these values out of plaintext Git. If you later expose Infisical through a hostname, update `SITE_URL` and configure the matching TLS route.

The Infisical Secrets Operator is configured to connect to the self-hosted service through cluster DNS and is applied only after Infisical is healthy. It is currently scoped to `minio-tenant`; add each future workload namespace to its scope and RBAC before syncing secrets there. MinIO's Application has automated sync disabled at your request; its current resources are left in place if already installed. The MinIO-specific Longhorn StorageClass and disk tags are removed for now. Recreate that StorageClass and disk selection before resuming MinIO; do not manually sync it until its `minio-env-configuration` secret source is configured.

## Apply flow

Argo CD itself is bootstrapped by `infra/argocd/pulumi`. The root Application discovers project and application manifests recursively. Each child Application uses its matching AppProject; no application uses Argo CD's `default` project. Argo CD needs read access to this Git repository and the Longhorn, CloudNativePG, Infisical, and MinIO Helm repositories.

Keep each component together as a module. AppProjects live in `projects/<project>/`; each Application lives in `applications/<project>/<application>/application.yaml`; and that application's Helm values and raw manifests live under the matching `values/<project>/<application>/` directory. Use descriptive chart-value filenames when a module has multiple charts, and put raw Kubernetes resources in that module's `resources/` directory. For example:

```text
applications/
├── security/
│   ├── infisical/application.yaml
│   └── infisical-secrets-operator/application.yaml
└── storage/
    ├── cloudnative-pg-operator/application.yaml
    ├── longhorn/application.yaml
    ├── minio/application.yaml
    ├── postgresql-cluster/application.yaml
    └── redis/application.yaml

values/
├── security/
│   ├── infisical/values.yaml
│   └── infisical-secrets-operator/values.yaml
└── storage/
    ├── longhorn/values.yaml and resources/
    ├── minio/tenant-values.yaml and resources/
    ├── postgresql-cluster/resources/
    └── redis/resources/
```

Add networking, observability, or Cilium policy directories when their first real manifests are ready; empty placeholders are not needed. Put Cilium policies under `policies/cilium/`. Keep secret values out of committed plaintext files.
